# Общая характеристика

## 1. Назначение системы

Информационная система документооборота предприятия с модулем автоматизации конфигурации серверной инфраструктуры предназначена для организации и автоматизации процессов подготовки, согласования, исполнения и документирования изменений конфигурации серверов предприятия.

Система объединяет электронный документооборот технической службы и инструменты автоматизированного управления серверной инфраструктурой. Она предоставляет единое пространство для регистрации документов на проведение конфигурационных работ, хранения сопроводительных материалов, согласования запланированных изменений и контроля результатов их выполнения.

В отличие от обычной системы обработки обращений, основным объектом системы является электронный документ, сопровождающий изменение на протяжении всего его жизненного цикла. Документ содержит сведения о планируемых работах, целевых серверах, параметрах конфигурации, результатах согласования и итогах исполнения.

Выполнение технических операций автоматизируется с помощью Ansible. После утверждения документа уполномоченный пользователь может инициировать запуск предусмотренного сценария настройки серверов. Система фиксирует ход выполнения, сохраняет технические журналы и формирует электронный акт по результатам работ.

Система ориентирована на внутренние процессы технического документооборота и администрирования серверной инфраструктуры предприятия.

## 2. Цели и задачи

Целью настоящего проекта является разработка информационной системы, обеспечивающей управляемый процесс изменения конфигурации серверной инфраструктуры посредством электронного документооборота и автоматизированного исполнения административных операций.

Для достижения обозначенной цели необходимо решить следующие задачи:

1. Разработать механизм создания, регистрации и хранения электронных документов, связанных с конфигурационными работами.
2. Реализовать ведение регистрационных карточек, версий документов, вложений и истории изменений.
3. Обеспечить согласование документов по установленным маршрутам с фиксацией решений и комментариев ответственных пользователей.
4. Реализовать ролевое разграничение доступа к функциям и данным системы.
5. Создать реестр обслуживаемых серверов с возможностью выбора целевых узлов для выполнения конфигурационных работ.
6. Интегрировать систему с объектным хранилищем для хранения файлов документов, вложений и сформированных отчётов.
7. Реализовать механизм асинхронного запуска сценариев Ansible для выполнения административных операций на целевых серверах.
8. Обеспечить отображение состояния выполнения задач, сбор технических журналов и сохранение результатов исполнения.
9. Реализовать автоматическое формирование электронного акта выполнения конфигурационных работ.
10. Организовать аудит действий пользователей и протоколирование выполнения технических операций.

## 3. Объект и предмет

### 3.1 Объект исследования
Объектом исследования являются процессы технического документооборота и управления изменениями конфигурации серверной инфраструктуры предприятия.

### 3.2 Предмет исследования
Предметом исследования являются методы и программные средства автоматизации регистрации, согласования и исполнения документов на конфигурационные работы, а также контроля результатов выполнения административных операций.

## 4. Границы проекта

### 4.1. Функции, входящие в проект

В рамках проекта предусматривается реализация следующих возможностей:

- создание, редактирование и регистрация документов на проведение конфигурационных работ;
- присвоение документам уникальных регистрационных номеров;
- ведение карточек документов, истории изменений и версий;
- загрузка, хранение и скачивание вложений;
- согласование документов с фиксацией решений и комментариев;
- управление статусами и жизненным циклом документов;
- ведение реестра целевых серверов и их основных параметров;
- разграничение доступа на основе ролей пользователей;
- запуск предусмотренных сценариев Ansible для утверждённых конфигурационных работ;
- выполнение длительных операций в фоновом режиме;
- отображение статусов и технических журналов выполнения;
- сохранение истории запусков и результатов выполнения;
- автоматическое формирование и хранение электронных актов;
- ведение журнала аудита действий пользователей.

### 4.2. Ограничения и функции, не входящие в первую версию

В первой версии проекта не предусматриваются:

- разработка универсальной системы электронного документооборота для всех подразделений предприятия;
- реализация кадрового, бухгалтерского и общего административного документооборота;
- произвольное выполнение пользовательских команд на серверах через веб-интерфейс;
- создание универсального конструктора Ansible-плейбуков непосредственно в интерфейсе;
- поддержка неограниченного набора типов серверов и административных операций;
- реализация полноценной высокодоступной распределённой инфраструктуры приложения;
- интеграция с внешними ERP-системами и системами мониторинга;
- разработка отдельного мобильного приложения.

Основной акцент первой версии делается на завершённом процессе работы с документом: от регистрации и согласования до автоматизированного исполнения конфигурационных работ и формирования итогового акта.

## 5. Функциональные подсистемы

Система разделяется на несколько взаимосвязанных функциональных подсистем.

### 5.1. Подсистема электронного документооборота

Предназначена для создания, регистрации и сопровождения документов, связанных с изменением конфигурации серверной инфраструктуры.

Основные функции:

- создание и редактирование документов;
- ведение регистрационных карточек;
- автоматическое присвоение регистрационных номеров;
- управление статусами документов;
- хранение истории изменений и версий;
- привязка документов к целевым серверам и конфигурационным работам;
- просмотр документов и истории их обработки.

### 5.2. Подсистема согласования

Обеспечивает рассмотрение и утверждение документов уполномоченными пользователями.

Основные функции:

- формирование и обработка маршрутов согласования;
- назначение согласующих лиц;
- фиксация решений о согласовании или отклонении;
- сохранение комментариев и времени принятия решений;
- контроль завершённости согласования;
- перевод утверждённых документов в состояние, допускающее исполнение работ.

### 5.3. Подсистема хранения документов и файлов

Обеспечивает хранение электронных документов и связанных с ними файлов.

Основные функции:

- загрузка и скачивание вложений;
- хранение технических заданий, конфигурационных файлов и отчётов;
- связь файлов с соответствующими документами;
- хранение версий файлов и контроль их целостности;
- сохранение сформированных электронных актов.

Для хранения файлов предусматривается использование MinIO — объектного хранилища с поддержкой API, совместимого с Amazon S3. Структурированные сведения о документах и файлах хранятся отдельно от содержимого самих файлов.

### 5.4. Подсистема учёта серверной инфраструктуры

Предназначена для ведения сведений о серверах, на которых могут выполняться конфигурационные работы.

Основные функции:

- регистрация и редактирование сведений о серверах;
- хранение сетевых параметров, адресов и сведений об операционной системе;
- группировка серверов по назначению и другим признакам;
- выбор целевых серверов при подготовке документа;
- формирование инвентаря серверов для Ansible на основе данных системы.

### 5.5. Подсистема автоматизации конфигурации

Обеспечивает выполнение административных операций на целевых серверах с помощью Ansible.

В первой версии предусматривается разработка сценариев для следующих типов операций:

1. Подготовка базового серверного окружения, включая развёртывание и настройку Nginx, PostgreSQL и Redis.
2. Обновление системных пакетов операционной системы с формированием отчёта.
3. Централизованное управление пользовательскими учётными записями и SSH-ключами доступа.

Основные функции подсистемы:

- выбор предусмотренного сценария конфигурации;
- передача параметров и перечня целевых серверов;
- запуск сценариев через Ansible Runner;
- выполнение длительных задач в фоновом режиме;
- получение и отображение состояния выполнения;
- сохранение результатов и технических журналов.

### 5.6. Подсистема безопасности и аудита

Предназначена для разграничения доступа и обеспечения прослеживаемости действий в системе.

Основные функции:

- аутентификация пользователей;
- назначение ролей и проверка разрешений;
- ограничение доступа к функциям в соответствии с ролью пользователя;
- регистрация операций с документами;
- фиксация действий по согласованию и запуску конфигурационных задач;
- хранение истории выполнения сценариев;
- сохранение технических журналов Ansible.

Предусматриваются два взаимосвязанных направления аудита: журнал действий пользователей и журнал технического исполнения конфигурационных операций.

### 5.7. Подсистема формирования результатов работ

Предназначена для документирования результатов выполнения конфигурационных операций.

Основные функции:

- получение результатов выполнения сценариев;
- фиксация итогового статуса работ;
- формирование электронного акта выполнения конфигурационных работ;
- включение в акт сведений об исходном документе, целевых серверах и результатах выполнения;
- сохранение акта и обеспечение его связи с исходным документом.

## 6. Роли пользователей

В системе предусматриваются следующие основные роли.

| Роль | Назначение | Основные возможности |
|---|---|---|
| Инициатор | Сотрудник, формирующий документ на проведение конфигурационных работ | Создание и редактирование документов в разрешённых статусах, прикрепление файлов, просмотр состояния и результатов своих документов |
| Согласующий | Пользователь, уполномоченный рассматривать документы | Просмотр направленных на согласование документов, принятие решений, добавление комментариев |
| Системный администратор | Специалист, отвечающий за выполнение конфигурационных работ | Просмотр утверждённых документов, выбор разрешённых сценариев, запуск задач, просмотр технических журналов |
| Администратор системы | Пользователь, отвечающий за настройку и обслуживание самой информационной системы | Управление пользователями, назначение ролей, настройка справочников и параметров системы |
| Аудитор | Пользователь, контролирующий историю действий и результаты операций | Просмотр журналов аудита, истории исполнения и доступных отчётов без изменения исходных записей |

Конкретный состав разрешений для каждой роли определяется отдельной матрицей ролевого разграничения доступа (RBAC).

Роли описывают логические категории полномочий. При необходимости одному пользователю могут назначаться несколько ролей.

## 7. Основные сценарии работы

### 7.1. Создание и регистрация документа

Инициатор создаёт документ, указывает обоснование и описание требуемых работ, выбирает целевые серверы и прикрепляет сопроводительные файлы.

После регистрации система присваивает документу уникальный номер и сохраняет его в реестре.

### 7.2. Согласование документа

Документ направляется по предусмотренному маршруту согласования. Уполномоченные сотрудники изучают сведения и вложения, принимают решения и при необходимости добавляют комментарии.

После завершения согласования документ получает статус, разрешающий переход к исполнению работ.

### 7.3. Исполнение конфигурационных работ

Уполномоченный пользователь выбирает разрешённый сценарий Ansible и запускает его для серверов, указанных в документе.

Задача передаётся на фоновое исполнение. Ansible Runner выполняет предусмотренные операции и предоставляет сведения о ходе выполнения.

### 7.4. Контроль результатов

Система отображает состояние выполнения задачи, сохраняет технические журналы и фиксирует результат операции.

При возникновении ошибок сведения о выполнении сохраняются для последующего анализа.

### 7.5. Завершение и формирование акта

По результатам исполнения система формирует электронный акт выполнения конфигурационных работ, сохраняет его и связывает с исходным документом.

Документ, акт и доступная история выполнения образуют единый комплект сведений о проведённом изменении инфраструктуры.

## 8. Архитектура системы

Предполагается использование клиент-серверной архитектуры с разделением пользовательского интерфейса, серверной бизнес-логики, хранения данных и исполнения фоновых задач.

Основные компоненты системы:

- **Клиентский уровень.** Веб-интерфейс для работы с документами, согласования, управления серверным реестром и просмотра результатов выполнения.
- **Серверный уровень.** API и бизнес-логика, отвечающие за обработку запросов, управление документами, проверку разрешений и взаимодействие между подсистемами.
- **Реляционная база данных.** Хранение структурированных данных, связей между сущностями и истории выполнения операций.
- **Объектное хранилище.** Хранение файлов документов, вложений и сформированных актов.
- **Контур фонового исполнения.** Очередь задач и рабочие процессы для выполнения длительных конфигурационных операций без блокировки пользовательского интерфейса.
- **Модуль автоматизации.** Взаимодействие с Ansible Runner и выполнение сценариев на целевых серверах по SSH.

Взаимодействие клиентского интерфейса с серверной частью предусматривается через REST API. В качестве основы серверной реализации рассматривается Python с FastAPI. Для хранения структурированных данных используется PostgreSQL, для файлов — MinIO, для фоновых задач — Celery и Redis, для автоматизации конфигурации — Ansible Core и Ansible Runner.

Окончательный состав компонентов и способы их взаимодействия уточняются при проектировании архитектуры.

## 9. Предварительный технологический стек

| Компонент | Предполагаемая технология | Назначение |
|---|---|---|
| Язык серверной части | Python | Реализация бизнес-логики и API |
| Backend-фреймворк | FastAPI | Обработка HTTP-запросов и предоставление REST API |
| СУБД | PostgreSQL | Хранение структурированных данных |
| Объектное хранилище | MinIO | Хранение документов, вложений и актов |
| Очередь фоновых задач | Celery | Асинхронное выполнение длительных операций |
| Брокер сообщений | Redis | Передача задач между компонентами |
| Автоматизация | Ansible Core | Выполнение конфигурационных сценариев |
| Интеграция с Ansible | Ansible Runner | Программный запуск сценариев и получение событий |
| Веб-интерфейс | Vue.js или React | Пользовательская часть системы |
| Взаимодействие компонентов | REST API, HTTP/JSON | Обмен данными между клиентом и сервером |
| Среда развёртывания | Docker, Docker Compose | Контейнеризация и запуск компонентов |

Приведённый стек является предварительным. Выбор конкретного фронтенд-фреймворка, структура API и детали развёртывания определяются на последующих этапах проектирования.

## 10. Ожидаемый результат проекта

Результатом проекта должна стать работающая веб-ориентированная информационная система, объединяющая технический документооборот предприятия и автоматизацию конфигурации серверной инфраструктуры.

Система должна обеспечивать полный цикл обработки документа на проведение конфигурационных работ: создание, регистрацию, согласование, исполнение, сохранение результатов и формирование итогового акта.

Практическая реализация должна продемонстрировать взаимодействие пользовательского интерфейса, серверной бизнес-логики, реляционной базы данных, объектного хранилища и модуля автоматизации Ansible.

Критерием завершённости проекта является возможность пройти сквозной сценарий на тестовой инфраструктуре: зарегистрировать документ, согласовать его, запустить предусмотренную конфигурационную операцию на целевом сервере, получить результат выполнения и сформировать связанный с документом электронный акт.

# Матрица разграничения прав доступа

## 1. Назначение

Матрица разграничения прав доступа определяет полномочия пользователей информационной системы документооборота предприятия с модулем автоматизации конфигурации серверной инфраструктуры.

Документ дополняет функциональные требования и варианты использования системы, определяя, какие операции доступны каждой роли.

Разграничение доступа осуществляется на основе ролевой модели (Role-Based Access Control, RBAC). Помимо роли пользователя, при выполнении операций учитываются состояние документа, принадлежность документа пользователю и другие условия, установленные бизнес-процессами системы.

## 2. Обозначения

| Обозначение | Значение |
|---|---|
| + | Операция разрешена |
| - | Операция запрещена |
| ~ | Операция разрешена с ограничениями, указанными в правилах доступа |

## 3. Роли пользователей

| Код | Роль | Описание |
|---|---|---|
| INITIATOR | Инициатор | Создаёт документы на выполнение работ, направляет их на согласование и отслеживает результаты. |
| APPROVER | Согласующий | Рассматривает документы и принимает решения о согласовании или отклонении. |
| SYSADMIN | Системный администратор | Управляет перечнем серверов, запускает разрешённые инфраструктурные операции и контролирует их выполнение. |
| ADMIN | Администратор системы | Управляет учётными записями, ролями и административными настройками системы. |
| AUDITOR | Аудитор | Просматривает документы, результаты работ и журнал аудита в целях контроля. |

Система не позволяет пользователю согласовать или отклонить собственный документ, даже если ему назначена роль согласующего. Административная роль сама по себе не предоставляет право согласования.

Запуск задания разрешается системному администратору только при выполнении установленных условий:

- документ согласован и находится в допустимом состоянии;
- пользователь имеет право выполнять соответствующую операцию;
- сценарий разрешён для данного вида работ;
- целевые серверы и параметры запуска прошли проверку;
- запуск регистрируется и связывается с исходным документом.

Повторный запуск допускается только в предусмотренных случаях, с учётом состояния предыдущего задания и правил безопасного повторения операции.

Акт не должен автоматически подтверждать успешное выполнение, если это не подтверждается результатами задания.

## 12. Правила применения матрицы

### 12.1. Ограничение доступа к объектам

Обозначение ~ применяется, когда операция разрешена только при выполнении дополнительных условий:

- инициатор имеет доступ к собственным документам;
- согласующий имеет доступ к документам из общей очереди согласования, кроме собственных документов;
- системный администратор имеет доступ к документам и результатам выполнения, необходимым для исполнения и контроля инфраструктурных работ;
- администратор системы имеет доступ к сведениям, необходимым для администрирования;
- аудитор имеет доступ к объектам, необходимым для проверки.

Конкретные правила доступа к документам и серверам должны быть реализованы на стороне сервера.

### 12.2. Разделение полномочий

Администрирование учётных записей, согласование документов и запуск инфраструктурных операций являются отдельными полномочиями. Наличие одной роли не предоставляет автоматически права, закреплённые за другой ролью.

### 12.3. Проверка состояния документа

Разрешение роли не отменяет проверку бизнес-условий. Например, системный администратор не может запускать сценарий по документу, который не прошёл согласование, а формирование акта требует наличия достаточных сведений о результатах работ.

### 12.4. Запрет по умолчанию

Если операция не предусмотрена матрицей или необходимые условия доступа не выполнены, система должна отказать в выполнении операции.

### 12.5. Регистрация значимых действий

Создание и изменение документов, решения о согласовании, изменения прав доступа, запуск инфраструктурных заданий и формирование электронных актов должны фиксироваться в журнале аудита.

## 13. Вопросы, требующие окончательного согласования

Перед реализацией системы необходимо уточнить:

1. Допускается ли назначение нескольких ролей одному пользователю.
2. Может ли инициатор редактировать документ, возвращённый на доработку.
3. Какие категории сведений доступны администратору системы.
4. Может ли системный администратор изменять состав доступных Ansible-сценариев или только выбирать из утверждённого перечня.
5. Какие операции разрешены с частично выполненными заданиями.
6. Как определяется область доступа аудитора.
7. Допускается ли удаление черновиков и сведений о серверах, связанных с историческими документами.

Окончательная матрица должна быть согласована с функциональными требованиями, вариантами использования и правилами обработки документов.

# Варианты использования системы (Use Cases)

## 1. Назначение

Настоящий документ описывает основные варианты использования информационной системы документооборота предприятия с модулем автоматизации конфигурации серверной инфраструктуры.

Система предназначена для управления документами, связанными с изменением серверной инфраструктуры: от создания и согласования документа до выполнения работ, фиксации результатов и формирования электронного акта.

## 2. Акторы системы

| Актор | Описание |
|---|---|
| Инициатор | Создаёт документ, описывает необходимые изменения и направляет его на согласование. |
| Согласующий | Рассматривает документ и принимает решение о возможности выполнения работ. |
| Системный администратор | Выполняет согласованные работы с использованием доступных Ansible-сценариев и анализирует результаты их выполнения. |
| Администратор системы | Управляет учётными записями, ролями и настройками системы. |
| Аудитор | Просматривает историю операций, сведения о выполненных работах и результаты исполнения документов. |

## 3. Основные варианты использования

### UC-01. Авторизация пользователя

**Основной актор:** пользователь системы.

**Цель:** получить доступ к функциям системы в соответствии с назначенной ролью.

**Предусловия:** пользователь зарегистрирован в системе и имеет действующую учётную запись.

**Основной сценарий:**
1. Пользователь открывает страницу авторизации.
2. Вводит учётные данные.
3. Система проверяет корректность учётных данных.
4. Система определяет назначенные пользователю права доступа.
5. Пользователь получает доступ к соответствующим разделам системы.

**Альтернативный сценарий:** при неверных учётных данных система сообщает об ошибке и не предоставляет доступ.

### UC-02. Создание документа на изменение инфраструктуры

**Основной актор:** инициатор.

**Цель:** зарегистрировать запрос на выполнение работ с серверной инфраструктурой и направить его на согласование.

**Предусловия:** инициатор авторизован в системе.

**Основной сценарий:**
1. Инициатор открывает форму создания документа.
2. Указывает наименование, обоснование и описание требуемых изменений.
3. Выбирает целевые серверы и указывает необходимые сведения о работах.
4. При необходимости прикладывает дополнительные файлы.
5. Система проверяет заполнение обязательных полей.
6. Система сохраняет документ и присваивает ему идентификатор или регистрационный номер. Документ получает статус черновика.
7. Инициатор проверяет заполненные сведения и отправляет документ на согласование.
8. Система повторно проверяет обязательные данные и допустимость отправки, после чего переводит документ в статус, соответствующий ожиданию согласования.

**Альтернативные сценарии:**
- Если обязательные поля не заполнены или данные некорректны, система сообщает об ошибках и предлагает исправить документ.
- Если инициатор не отправляет документ на согласование, документ остаётся черновиком и не может использоваться для запуска инфраструктурных работ.

### UC-03. Согласование документа

**Основной актор:** согласующий.

**Цель:** определить, разрешено ли выполнение указанных в документе работ.

**Предусловия:**
- Документ создан и направлен на согласование.
- Документ доступен согласующему для рассмотрения.
- Согласующий не является автором рассматриваемого документа.

**Основной сценарий:**
1. Согласующий открывает общую очередь документов, ожидающих рассмотрения.
2. Выбирает документ и просматривает его содержание, обоснование, перечень работ и целевые серверы.
3. Принимает решение о согласовании документа.
4. Система проверяет, что документ всё ещё ожидает решения и что согласующий не является его автором.
5. Система сохраняет решение, сведения о согласующем и время операции.
6. Статус документа обновляется.

**Альтернативные сценарии:**
- Согласующий отклоняет документ с указанием причины. Система сохраняет решение и причину отклонения, после чего документ получает соответствующий статус.
- Если документ уже обработан или согласующий является его автором, система не позволяет принять решение и сообщает о причине отказа.

### UC-04. Просмотр и поиск документов

**Основной актор:** авторизованный пользователь.

**Цель:** найти документ и ознакомиться с его текущим состоянием.

**Предусловия:** пользователь авторизован и имеет право просматривать соответствующие документы.

**Основной сценарий:**
1. Пользователь открывает раздел документов.
2. Просматривает список доступных ему документов.
3. При необходимости задаёт параметры поиска или фильтрации: регистрационный номер, наименование, статус или дату создания.
4. Система отображает подходящие результаты.
5. Пользователь открывает выбранный документ и просматривает его содержание, историю согласования и сведения о выполнении работ в пределах своих прав.

### UC-05. Управление перечнем серверов

**Основной актор:** системный администратор.

**Цель:** поддерживать актуальный перечень серверов, на которых могут выполняться разрешённые инфраструктурные работы.

**Предусловия:** пользователь авторизован и обладает необходимыми правами.

**Основной сценарий:**
1. Системный администратор открывает раздел управления серверами.
2. Просматривает сведения о зарегистрированных серверах.
3. Добавляет новый сервер либо изменяет доступные для редактирования сведения о существующем сервере.
4. Система проверяет введённые данные и сохраняет изменения.
5. Обновлённые сведения становятся доступны при подготовке и выполнении соответствующих работ.

**Примечание:** учётные данные и секреты для подключения к серверам должны храниться и обрабатываться с соблюдением требований безопасности.

### UC-06. Запуск согласованных инфраструктурных работ

**Основной актор:** системный администратор.

**Цель:** выполнить разрешённые работы на целевых серверах с использованием Ansible.

**Предусловия:**
- Документ согласован и допускает выполнение работ.
- Для документа определены целевые серверы и необходимые параметры.
- Пользователь имеет право запускать инфраструктурные операции.
- Требуемый Ansible-сценарий входит в перечень разрешённых сценариев и доступен системе.

**Основной сценарий:**
1. Системный администратор открывает согласованный документ.
2. Проверяет содержание работ и целевые серверы.
3. Выбирает разрешённый Ansible-сценарий и задаёт предусмотренные им параметры.
4. Система проверяет статус документа, права пользователя, целевые серверы и допустимость выбранной операции.
5. Система создаёт задание на выполнение работ.
6. Исполнение Ansible-сценария запускается в фоновом режиме.
7. Система сохраняет сведения о запуске и отображает текущий статус задания.

**Альтернативные сценарии:**
- Если документ не согласован или его статус не допускает выполнение, система запрещает запуск.
- Если пользователь не обладает необходимыми правами, система отклоняет запрос.
- Если выбранный сценарий не входит в перечень разрешённых или параметры некорректны, система не запускает задание и сообщает об ошибке проверки.
- Если задание не удалось запустить, система фиксирует ошибку и предоставляет сведения о её возникновении.

**Ограничение:** запуск произвольных команд через интерфейс системы не допускается. Инфраструктурные работы запускаются только для согласованного документа и с использованием разрешённых Ansible-сценариев.

### UC-07. Контроль выполнения работ

**Основной актор:** системный администратор.

**Цель:** отслеживать выполнение Ansible-сценария и получать информацию о его результате.

**Предусловия:** задание на выполнение инфраструктурных работ создано.

**Основной сценарий:**
1. Системный администратор открывает сведения о задании.
2. Система отображает текущий статус выполнения.
3. По мере поступления данных система сохраняет и предоставляет доступные сведения о ходе выполнения и журнале операций.
4. После завершения задания система фиксирует итоговый результат.
5. Сведения о результате связываются с соответствующим документом.

**Альтернативные сценарии:**
- При ошибке система фиксирует неуспешное выполнение и доступные сведения об ошибке.
- Если работы выполнены только на части целевых серверов, система фиксирует результат по каждому доступному серверу и отражает частичное выполнение, если оно подтверждается полученными данными.

**Ограничение доступа:** системный администратор просматривает сведения, необходимые для выполнения работ. Другие роли могут просматривать доступные им статусы и результаты через карточку документа в соответствии с матрицей доступа.

### UC-08. Формирование электронного акта

**Основной актор:** системный администратор.

**Цель:** сформировать документ, фиксирующий фактические результаты выполненных работ.

**Предусловия:** выполнение задания завершено, а система располагает необходимыми сведениями о результатах.

**Основной сценарий:**
1. Системный администратор открывает документ с завершёнными работами.
2. Просматривает итоговый результат исполнения, включая сведения об ошибках или частичном выполнении, если они имеются.
3. Инициирует формирование электронного акта.
4. Система формирует акт на основании сведений об исходном документе и фактических результатах выполнения работ.
5. Система сохраняет акт и связывает его с исходным документом.
6. Пользователи с соответствующими правами могут просмотреть или скачать сформированный акт.

**Альтернативные сценарии:**
- Если система не располагает достаточными сведениями для формирования акта, она сообщает о невозможности завершения операции.
- Если задание завершилось ошибкой или выполнено частично, акт при наличии необходимых данных может отражать фактический результат, но не должен обозначать работы как успешно выполненные в полном объёме.

**Ограничение:** сформированный акт нельзя редактировать напрямую. Исправление или повторное формирование выполняется по предусмотренной системе процедуре с сохранением истории операций.

### UC-09. Просмотр журнала аудита

**Основной актор:** аудитор.

**Цель:** получить сведения о действиях пользователей и изменениях состояния документов и заданий.

**Предусловия:** аудитор авторизован и имеет право доступа к журналу аудита.

**Основной сценарий:**
1. Аудитор открывает журнал аудита.
2. Выбирает необходимые параметры поиска или фильтрации.
3. Система отображает доступные записи о действиях пользователей, изменениях статусов, согласованиях и выполнении инфраструктурных работ.
4. Аудитор открывает запись и просматривает подробные сведения в пределах предоставленных прав.

### UC-10. Управление пользователями и ролями

**Основной актор:** администратор системы.

**Цель:** управлять учётными записями пользователей и их правами доступа.

**Предусловия:** администратор системы авторизован и обладает соответствующими полномочиями.

**Основной сценарий:**
1. Администратор открывает раздел управления пользователями.
2. Создаёт учётную запись, изменяет сведения о пользователе или блокирует доступ при необходимости.
3. Назначает или изменяет роль пользователя.
4. Система проверяет допустимость операции и сохраняет изменения.
5. При последующих обращениях система применяет обновлённые права доступа.

## 4. Общий сценарий работы системы

Основной бизнес-сценарий системы включает следующие этапы:

1. Создание документа инициатором и сохранение его как черновика.
2. Проверка и отправка документа на согласование.
3. Рассмотрение документа согласующим, который не является автором документа.
4. Подготовка и запуск разрешённого Ansible-сценария системным администратором.
5. Контроль выполнения работ и фиксация фактических результатов, включая ошибки и частичное выполнение.
6. Инициирование системным администратором формирования электронного акта на основании результатов.
7. Хранение истории операций и результатов для последующего аудита.

Переход к выполнению инфраструктурных работ допускается только при соблюдении установленных условий согласования и прав доступа. Конкретные названия статусов и полный перечень переходов между ними определяются при проектировании бизнес-процессов.

## 5. Ограничения и границы системы

- Система не предназначена для произвольного выполнения команд на серверах без предусмотренных механизмов контроля.
- Выполнение инфраструктурных работ осуществляется только для согласованных документов и с использованием разрешённых Ansible-сценариев.
- Возможность просмотра документов, запуска работ, управления серверами и доступа к журналам определяется правами пользователя.
- Пользователь не может согласовать документ, автором которого он является, даже если ему назначена роль согласующего.
- Результаты выполнения работ, включая ошибки и частичное выполнение, сохраняются в связи с исходным документом.
- Электронный акт формируется на основании фактических результатов выполнения работ. Акт не должен представлять частичное или неуспешное выполнение как успешное выполнение в полном объёме.
- Сформированный акт не редактируется напрямую; повторное формирование или исправление выполняется по предусмотренной системе процедуре с сохранением истории операций.
- Юридический статус акта и необходимость электронной подписи определяются отдельными требованиями к системе.
